# WhatIF 3.2 harness protocol qualification

The new adapter executes seven fixed Bastion CLI scenarios: verified receipt reuse, unapproved execution refusal, digest refusal, changed-input refusal, foreign cursor refusal, report tamper detection and cancellation before execution. The actual 0.7 Bastion campaign issued 25 CLI command calls; all seven scenarios passed. A fresh process checked hashes and independently re-evaluated its fixed assertions from retained command responses. No HTTP requests or provider calls were made.

Six new adapter tests passed, including planning without execution, source/digest acknowledgement, malformed output, output caps, actual Bastion integration and recomputed-hash oracle tampering. The focused harness/MCP test invocation passed eight tests. Source-pin and budget failure cases deliberately use reviewed fake fixture code; they are control tests, not real-provider evidence.

## Usage and scope

See [harness campaign instructions](../skills/whatif/references/harness.md). The plan names trusted local source and an interpreter. Execution is unsandboxed host code with a reduced child environment and isolated Python import mode, not a new general shell interface. The loaded 3.1 plugin does not gain the three new MCP tools until its normal update/reload flow. This source update does not alter user permissions, replace the system Node installation or mutate production apps.

Verification re-evaluates retained response oracles; it does not reconstruct every fixture database or provide a signed attestation. A party with equal filesystem authority can fabricate an internally consistent local evidence set. No OpenClaw or DeepClaw instance was run, and no superiority claim is established.
